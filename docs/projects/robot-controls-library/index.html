Robot Controls Library

Our team’s own lightweight motion-control library, replacing the public one we’d relied on. It puts what I’ve learned in classes to work, accepts third-party sensors, tunes its own PID gains, and measures its own tracking wheel offsets.

Status
In progress
Date

Built with

Work in progress. This library is still being developed, so some of the writing, videos, and pictures here may be incomplete.

My team has previously used LemLib, a public motion-control library for VEX V5 robots developed by other teams. It served us well, but it’s no longer being actively updated, it can feel sluggish at times when writing autonomous routes, and since it’s built to cover everyone’s robots, it carries more than we need. This year I’m developing our own library to replace it, kept lightweight for our purposes. It has two main goals: apply what I’ve learned in my classes to improve the robot’s performance overall, and make the library extensible so it can grow with our future needs, such as integrating third-party sensors alongside the stock hardware. Along the way I added two features of my own: automatic tuning of PID constants, and automatic tracking wheel offsets.

Memory efficiency

Since the library only has to serve our robots, I kept it to what we actually use and designed how it stores and manages its state to keep its memory footprint small, leaving more room for the rest of the robot’s code.

Third-party sensors

Sensors outside the stock VEX lineup can feed into the library alongside VEX’s own hardware.

Auto-tuning PID constants

Tuning PID constants by trial and error is slow and never quite finished, so I wrote an autotune that measures the drivetrain and works the gains out from that. It runs in three stages: measure, compute, and verify. The charts below come from one real turning autotune on my test robot, about 14 seconds from start to finish. Driving is tuned the same way, using short drives forward and back in place of spins.

Measure. The robot spins in place twice at two fixed power levels, with no feedback. From how quickly it speeds up and how fast it ends up turning, the autotune measures four things: the power it takes just to overcome friction, how much speed each extra unit of power adds, how long the speed takes to build up, and the delay before it starts responding at all.

Compute. Each measurement maps onto a gain. Friction becomes a feedforward term that cancels it. The build-up time sets kD, which cancels the lag. The speed per unit of power and the delay together set kP, as high as it can go while staying critically damped, which means reaching the target as fast as possible without overshooting. No integral term is needed, since the friction term already removes the steady error that friction would otherwise leave.

Verify. The model is a simplification, so I don’t trust it blindly: the gains are checked on the robot with real 90° turns. After each turn kP goes up if the turn landed cleanly and down if it overshot, and the largest kP that didn’t overshoot is kept. On this run the model turned out to be cautious: the search climbed from kP 0.44 to 0.91 before a turn overshot, cutting the turn from 1.8 s to 0.68 s.

Tracking wheel auto offsets

Odometry depends on knowing exactly where each tracking wheel sits on the chassis. Rather than measuring those offsets by hand, I made the library calibrate them automatically.
